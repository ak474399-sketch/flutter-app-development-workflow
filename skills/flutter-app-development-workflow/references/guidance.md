# 问题引导与用户验收

阶段模板见 [stage-prompts.md](stage-prompts.md)，实际验收卡见 `../assets/templates/acceptance.md`；执行检查不生成用户同意。

## 当前阶段提问
1. 先提取已确认决定和实际材料；明确缺的是资料、产品决定还是验证证据。
2. 每轮只集中处理影响当前阶段的少量问题。给推荐、理由及对工作范围、体验、时间／费用的具体影响。用户无需先写技术方案。
3. 基于现有页面提出具体差异，例如“参考引导有五页，本轮是否保持，还是按你之前的三页决定？”；不要重问已经确认的规则。
4. 资料不支持结论时直接说明未知和取得证据的方式；不要用提问暗示该功能必然存在。
5. 给用户方案、流程或实际页面后让其判断；技术实现由 agent 负责。产品规则、费用或数据处理发生变化时说明影响再对齐。

## 验收卡（每大阶段）
- 本阶段范围版本与已确认标准。
- 可打开的具体产物、版本及文件路径。
- 已执行验证：环境、步骤、结果、证据。
- 未完成／未验证／失败事项与影响。
- 用户可直接检查的操作或对照项。
- 用户决定：通过／修改后再验／不适用／明确接受有限范围。

“可以”只有在上下文明确是对本阶段产物的验收时才记为验收；对执行方案的“可以”只授权执行，不等于产物通过。不得由 agent 或检查脚本生成虚假的用户确认。

## 变更与恢复
保存原决定、用户新指令、影响阶段和旧产物。新范围使用新 revision；依赖阶段重验。恢复时先看交接、现行决定、当前产物清单，再核对源码／连接／配置／安装版本等易变事实。用户占用手机、供应商故障等只阻断依赖工作，保留可独立进行的工作。

## 行为检查场景
- 只给 APK 包名：先定位已有逆向资料；输出阶段概览和资料缺口，不自行创建市场定位。
- 仅批准设计方向：可做设计范围内工作，不宣称页面／业务已验收。
- 用户说“页面都做好了就接 AI”：先核对 UI 用例与现有验收，列缺口，然后明确 AI 输入输出及失败范围。
- 选择不接广告／订阅：仍准备必选基础 SDK，商业化分支由用户确认不适用。
- 没有商店配置：完成可做工程，商品／支付／后台归因保持未验，不能模拟成功冒充真实结果。
